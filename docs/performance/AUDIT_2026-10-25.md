## Duplicate PIXI stage render — reproduced and fixed locally

Hypothesis from the renderer audit was confirmed by `tools/perf/check-render-count.cjs`, which enters Arcade through the UI and wraps the real renderer methods. In a three-second gameplay window the original renderer produced **180 draw calls and 360 renderer.render calls**. The one-render-per-draw assertion failed before the change. Saved `render-count-baseline.json`.

Cause: PIXI Application installs its own render listener on the application ticker. Calling `app.ticker.stop()` prevents scheduled ticker work, but manually calling `app.ticker.update(now)` still runs that listener. Poly Oracle then explicitly rendered the stage again in the same `draw()` call.

Fix: remove only `app.render` with its application context from the application ticker during renderer initialization. Keep manual ticker updates for effect callbacks and keep the existing explicit stage render. No gameplay rates, visual quality settings, or weapon rules were changed. Generated bundle rebuilt with `npm run prepare:web`.

Regression test additionally counts a callback attached to the effect ticker, requiring it to advance once per game draw. Native CPU/thermal impact is not yet measured: installed phone app still contains the old behavior. Halving this stage-render count must not be described as halving overall CPU, GPU work, or battery use. Paused-menu retained work remains a separate open investigation.

Post-fix result: **180 draws, 180 stage renders, 180 effect-ticker callback invocations**. Test passed; saved `render-count-after.json`. Renderer syntax check, targeted ESLint (no errors), web preparation, and diff whitespace check passed.

## Slot underlay rendering — PERF-04 root cause, fixed (PERF-02)

Cause: level win → scorecard → `handoffAfterScorecard()` → `enterSlot()` never stops the gameplay loop. The gameplay `frame()` had no `isSlotActive()` check, so the full update/draw (PIXI stage + 2D canvas) and the separate `galaxyBackground` starfield loop kept rendering at full rate behind the opaque cabinet. (Backgrounding during the slot already stops the loop, and the slot's `onExit` restarts it, so a stopped loop during the slot is an existing supported state.)

`tools/perf/check-slot-underlay.cjs` opens the real slot with the gameplay loop left running, as the real flow does. Baseline: **90 gameplay draws and 1,440 starfield paint operations per 3 s, both during gameplay and under the slot** (`slot-underlay-baseline.json`).

Fix (`script.js`):
- `frame()` idles while `isSlotActive()`: it reschedules rAF and resets `sim.last` without updating or drawing. PIXI is not destroyed, so leaving the slot pays no renderer re-init.
- `enterSlot()` hides the starfield if visible (`slotHidGalaxyBg`); `slotTeardown()` restores it. The slot's ← Modes path relies on that restore because `showModeSelect()` doesn't re-show the starfield; `startLevel()` re-shows it on the normal exit.

Post-fix browser check: 0 draws and 0 starfield ops under the slot; after ← Modes, the starfield is `display:block` and painting (1,440 ops/3 s). Slot reel-redraw and render-count regressions still pass (`slot-underlay-after.json`).

## Paused Arcade → menu — PERF-03 root cause, fixed locally

Device baseline on PERF-02 (user paused a game to the Modes menu, 45 s, 44 samples/process, thermal Serious): WebContent **18.05%** (fresh menu 4.15%), WebKit GPU 40.55% (fresh 36.18%), backboardd 36.28% (fresh 26.15%). Summary: `ios-perf02-menu-after-gameplay.json`.

`tools/perf/check-paused-menu.cjs` counts canvas ops per canvas plus CDP task/script time over 4 s windows: fresh menu, gameplay, menu after ← Modes, after Resume. ## Gameplay Time Profiler — layer repaints and buffer churn

30 s all-process Time Profiler during gameplay (stars-off build; the user moved on to the slot partway through). `tools/perf/summarize_timeprofile.py` gives per-thread/leaf summaries; inclusive attribution was done ad hoc. WebKit GPU process inclusive: `RemoteRenderingBackend::prepareImageBufferSetsForDisplay` → `ensureBufferForDisplay` → `allocateImageBuffer` → `IOSurface::create` ~11%; `WebCore::Gradient::paint` ~7.5% with `platformConvertColorComponents` ~7.3%. In other words, WebKit kept repainting layers into freshly allocated buffers and painting gradients with per-pixel color conversion. backboardd time is dominated by the CoreAnimation display thread with IOSurface lookup/transaction work.

Browser tracing (`tools/perf/check-canvas-churn.cjs`, `tools/perf/check-layer-paints.cjs`) found no gameplay canvas resizing, but:

- **Ten HUD writes every frame** (60/s each): score, level, lives, run timer, multiplier text; timer `class` (classList.remove of absent classes still rewrites the attribute); timer backdrop `class`; quad/pulse badge `aria-hidden`; missile `disabled`. Plus a per-frame `getBoundingClientRect` for the countdown position.
- **`setGalaxyBackgroundDim()` rewrote `#bgTint`'s full-screen double radial-gradient background** whenever the timer ratio's third decimal changed (~3/s), repainting a full-screen gradient layer at 3×. This matches the GPU-process gradient and large-IOSurface work.

Fix (PERF-04): `setTextIfChanged` / `setAttrIfChanged` / `setStyleIfChanged` helpers in the per-frame HUD writers, `toggle(x, false)` instead of `remove`, countdown positioning only while the number shows; `#bgTint` gradients are now static CSS with a ratio-1 overlay (`.bgTint::after`) faded in via `--bg-dim` opacity (2-decimal). Browser: per-frame HUD mutations 3,000 → ~7 per 5 s (`layer-paints-baseline.json` → `layer-paints-after.json`); remaining writes are commander ticker/portrait and the run timer once per second. All earlier perf regression checks pass. Device measurement pending.

Also in PERF-04 (non-perf): plasma net charge 800 → 150 ms (GAME-01) and iOS portrait-only orientation lock (`UIRequiresFullScreen` added for iPad).
